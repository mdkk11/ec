# Explained Code Review の可読性・Plan照合改善計画

## 1. 背景と目的

`explained-code-review` は、Git差分を実装意図ごとにまとめ、Blind reviewとPlan reviewを分離したHTMLレビューを生成している。一方、現在の画面は差分の追加・削除を背景色で示すだけで、構文の区別がなく、長いhunkを読む負荷が高い。また、Plan照合結果はreportへ保存されるものの画面に表示されず、Planの各項目と実装・テストの対応も確認できない。

本変更では、次の状態を目標とする。

- コードをShikiで構文強調し、light/darkの両テーマで読みやすくする。
- 通常の指摘確認と、ファイルごとの実装理解を別の表示モードに分ける。
- Plan項目ごとの充足状態と根拠を、変更グループ・ファイル・差分位置へ辿れる形で表示する。
- 大きな差分でも、承認単位である実装意図グループを壊さず、コードを小さな説明区間に分けて読めるようにする。
- 既存のBlind review分離、固定snapshot、`file://`、CDNなし、通常実行時Node.js 20以上＋Gitのみという保証を維持する。

## 2. 現状調査

### 調査済みの事実

- `report-schema.json` v2の変更グループは、`intent`、`implementationSummary`、`impact`、`verificationPoints`と、配下の全file・hunk・findingを持つ。
- UIは変更グループを1件選び、そのグループの全hunkを連続表示する。1hunkは400行ずつ描画するが、説明単位はhunkより細かくならない。
- 生成済みreportでは、1グループに2,239行、別reportでは3,552行のdiffが含まれている。400行ページングはDOM量を抑えるが、読む単位は依然として大きい。
- コード表示は等幅フォント、追加・削除・finding位置の背景色だけで、言語別のtoken colorを持たない。
- `stages.plan.summary`と`planPath`はreportへ入るが、`review.js`はPlan summaryを描画していない。
- Plan項目とgroup、file、test、diff位置を結ぶschemaが存在しない。
- findingは問題指摘を表す。正常な実装の説明をfindingへ混ぜると、未解決件数とレビュー完了判定の意味が崩れる。
- 現在のSkillは通常利用先のpackage manager・`node_modules`・外部CDNに依存せず、生成HTMLを`file://`で開く設計である。
- Shikiは[fine-grained bundle](https://shiki.style/guide/bundles)、JavaScript RegExp engine、[light/dark dual theme](https://shiki.style/guide/dual-themes)を提供しており、必要言語とthemeをbuild時に固定できる。

### 現在の主な変更対象

- `.agents/skills/explained-code-review/SKILL.md`
- `.agents/skills/explained-code-review/references/review-rules.md`
- `.agents/skills/explained-code-review/references/report-schema.json`
- `.agents/skills/explained-code-review/scripts/collect-diff.mjs`
- `.agents/skills/explained-code-review/scripts/generate-report.mjs`
- `.agents/skills/explained-code-review/assets/review-template.html`
- `.agents/skills/explained-code-review/assets/review.css`
- `.agents/skills/explained-code-review/assets/review.js`
- Skill単体のunit、portable、Playwright UI test、README、package manifest、lockfile

## 3. 解決する問題

1. コードの字句が視覚的に区別されず、長いTypeScript、JSON、CSS、Markdownなどを追いにくい。
2. 実装意図グループの説明が全体要約に留まり、各ファイルが何を担当し、各コード区間がなぜ必要かを確認できない。
3. Plan照合が全体summaryだけで、要件の充足、部分対応、未実装、対象外と、その根拠を項目単位で判断できない。
4. 大差分時に1グループのコード量が大きくなるが、グループを細分化すると承認単位と実装上のまとまりが失われる。
5. 詳細解説を常に生成すると、小さい差分でも分析時間、token量、report量が増える。

## 4. 採用する方針

### 4.1 2モード構成

collectorへ`--explain review|walkthrough`を追加し、既定値を`review`にする。

- `review`: 現在のBlind finding、Plan coverage、実装意図グループ、raw diffを中心に確認する既定モード。小さい差分やPR前の指摘確認に使う。
- `walkthrough`: `review`の全内容に加え、ファイル別の責務・実装要約と、hunk内の説明区間を生成する。コードを理解・引き継ぎするときに使う。

`walkthrough`で生成した画面には「レビュー」と「ファイル別解説」のview switchを表示する。`review`で生成した画面には存在しない詳細viewを見せず、未生成データをクライアント側で推測しない。

Skillは利用者が「ファイルごとに詳しく」「実装を解説して」「walkthrough」と依頼した場合に`walkthrough`を選び、それ以外は`review`を使う。実行後にモードを変える場合はsnapshotを再収集してreportを再生成する。

### 4.2 承認グループと説明区間を分離する

実装意図グループは引き続き承認単位とし、file単位や一定行数だけを理由に分割しない。詳細な説明はgroup配下の`fileExplanations`と`segments`へ置く。

`walkthrough`のtext fileは次の規則で説明する。

- navigationと説明の所有単位を`(groupId, fileId)`とする。同じpathのhunkが複数groupへ分かれる場合は、groupごとに別項目としてgroup名を併記する。
- groupに割り当てられたhunkだけを対象に、fileごとの`responsibility`、`implementationSummary`、確認観点を1件作る。
- file explanationは`detailLevel: segmented | summary-only`を持つ。
- `segmented`の各hunkを論理的な変更単位の`segment`へ分け、1segmentは最大120 diff行とする。
- segmentは同じhunk内の連続した0-based line index範囲を持ち、`segmented` hunkの全行を重複・欠落なく覆う。
- 同じ目的の隣接区間は統合し、異なる責務を行数上限まで詰め込まない。120行で分割した連続segmentは前後関係を明記する。
- segmentには「何を変えたか」「なぜ必要か」「レビュー時に見る点」を各1〜2文で記載し、1行segmentの乱造や同じ説明の反復を避ける。
- findingはsegmentへ関連付けられるが、説明そのものをfindingとして数えない。
- `summary-only`は`summaryOnlyKind: binary | lockfile | source-map | minified | generated`と理由を持ち、コード区間解説を作らない。

summary-only判定はcollectorが決定し、Stage 1が任意に選ばない。対象はbinary、`pnpm-lock.yaml`、`package-lock.json`、`yarn.lock`、`bun.lock`、`bun.lockb`、source map、拡張子が`.min.js`または`.min.css`のfile、および先頭5行にコメント行として`@generated`、`generated file`、`generated by`、`do not edit`のいずれかで始まる生成物bannerを持つfileとする。通常ソースの文字列literalや説明文に同じ語句が含まれるだけではsummary-onlyにしない。generatorはcollectorの分類と`detailLevel`の一致を検証し、`segmented`だけに全行coverageを要求する。

walkthroughはsummary-onlyを除くtext diffが20,000行を超える場合、truncateや説明省略をせず停止し、baseまたはscopeを狭めるよう案内する。Stage 1は4,000 diff行またはraw text 1 MiBの早い方を上限にBlind batchへ分ける。1hunkだけで上限を超える場合はそのhunkを単独batchにし、segment規則は維持する。各batchはPlanを受け取らない独立contextで分析し、最後にPlanを受け取らないBlind consolidatorがgroupを統合する。Stage 1 JSONを固定した後にだけ親contextがStage 2を開始する。

### 4.3 Plan coverageを第一級データにする

report schemaをv3へ上げ、top-levelへ`planCoverage`を追加する。Planありでは、Stage 2がPlanの見出し・箇条書き・静的に判定できる完了条件をレビュー可能な項目へ整理し、次を出力する。

```text
planCoverage.items[]
  id
  label
  startLine / endLine
  status: satisfied | partial | missing | not-applicable
  rationale
  evidence[]: groupId + file + startLine/endLine または groupIdのみ
  findingIds[]
```

- coverage itemにするのは、差分から静的に判定できる実装、test code、文書の要件だけとする。
- `satisfied`は実装またはtestの具体的なevidenceを必須とする。
- `partial`と`missing`は不足内容と1件以上のStage 2 finding参照を必須とする。
- `not-applicable`は差分scope外または明示的対象外である理由を必須とする。
- groupは`planItemIds`を持ち、Plan項目からgroupへ、groupからPlan項目へ双方向に辿れるようにする。
- Plan本文全体はfinal reportへ複製しない。項目label、Plan内のline range、照合理由だけを保存する。
- Planなしでは`status: skipped-no-plan`、`items: []`とし、画面へ「Plan照合なし」を明示する。

コマンド成功、目視確認、性能値など、実行結果がなければ判定できないPlan項目はtop-levelの`verificationItems`へ分離する。各項目はPlan内のlabelとline range、`requiredAction`、`status: not-verified`を持つ。このSkillはreview生成中にrepositoryのtest commandを暗黙実行せず、test fileの存在を成功証拠として扱わない。実行結果の取込みは今回の対象外とし、画面とfeedbackへ未確認事項として表示する。

Stage 1 / Stage 2の許可変更範囲を次へ固定する。

- Stage 1は引き続きPlanを読まない。
- Stage 1のgroup ID、hunk割当、group説明、walkthroughのfile explanation・segmentをgroup ID単位で完全保持する。
- S1 findingは元group、ID、本文、location、severityを保持し、Stage 2は`planAssessment`だけを更新できる。group/hunk対応をBlind結果として固定するため、現行のgroup間移動許可は廃止する。
- Stage 2はS2 finding、group/file explanationの`planItemIds`、top-levelの`planCoverage`と`verificationItems`だけを追加できる。
- generatorはStage 1とfinal analysisを比較し、上記以外の追加・削除・変更を拒否する。

### 4.4 Shikiをbuild済みassetとして同梱する

Skill開発依存へ`shiki@4.3.1`と`esbuild@0.28.1`を正確なversionで追加する。`scripts/build-syntax-highlighter.mjs`でfine-grained bundleを生成し、commit対象の`scripts/syntax-highlighter.bundle.mjs`として同梱する。

- engineはWASM不要のJavaScript RegExp engineを使う。
- themeは`github-light`と`github-dark`を使い、tokenへlight/dark両方の色を持たせる。
- 対応言語はTypeScript、TSX、JavaScript、JSX、JSON、JSONC、HTML、CSS、SCSS、Markdown、MDX、YAML、Bash、SQL、Python、Go、Rust、Java、Kotlin、Swift、C、C++、C#、Ruby、PHPとする。
- pathの拡張子と代表的file名から言語を決め、対応外、判定不能、Git metaはplain textへfallbackする。
- old streamはcontext＋deletion、new streamはcontext＋additionでtokenizeする。additionとcontextにはnew stream、deletionにはold stream、metaと`No newline` markerにはplain textを採用する。hunk開始前のgrammar stateは復元せず、hunk内だけを強調範囲とする。
- token textをreportへ複製せず、diff lineの元`text`に対するUTF-16の`start`、`end`、`styleId`だけを`tokenRuns[]`へ保存する。隣接する同一styleは結合し、UIは`line.text.slice(start, end)`を`textContent`へ設定する。
- light/darkの`color`、`fontStyle`、`fontWeight`、`textDecoration`はtop-levelの重複なし`highlighting.styles[]`へ置き、token runはstyle IDで参照する。plain text fallbackでは`tokenRuns`を空配列にし、元行をそのまま描画する。
- generatorはrunの範囲、重複、style参照と、runから復元した文字列が元の`line.text`と一致することを検証する。不一致はデータ破損として生成を停止する。
- report top-levelの`highlighting`へShiki version、engine、theme名、style table、`fallbacks[]`を記録する。fallbackはhunk IDと`unsupported-language | token-limit | report-size | time-budget | tokenize-error`の理由を持つ。
- 1hunkの元textが1 MiBを超える場合はtokenize前に、token runが100,000件を超えるか、token JSON byteが元hunk textの4倍＋短いhunkの構造overhead用256 bytesを超える場合はtokenize後に、そのhunkをplain textへfallbackする。
- highlight処理はgenerator全体で10秒のdeadlineを持ち、各同期tokenizeの前後で超過を検出する。超過した現在hunkの結果は採用せず、現在hunkと後続hunkを`time-budget`でfallbackする。同期tokenize呼出し自体は途中中断できないため、10秒はwall-clockの強制終了ではなく結果採用のdeadlineとする。clockはtest時に注入可能にする。
- 最終`report.json`は64 MiBを上限とする。超える場合はhighlight payloadが大きいhunkから`report-size` fallbackへ変えて再計算し、全highlightを外しても超える場合だけ明示errorで停止する。
- UIはtokenを`textContent`でspanへ入れ、Shikiが返した色・font styleだけを許可済みfieldから適用する。Shiki HTMLをそのまま`innerHTML`へ渡さない。
- theme切替は既存の`data-theme`と連動し、追加・削除・finding highlightの背景色をtoken色より背面へ置く。

通常のreview生成ではcommit済みbundleだけをimportするため、移植先で`pnpm install`を要求しない。`pnpm build:highlighter`はSkill開発時と依存更新時だけ実行する。

Shiki、同梱theme、grammarのlicenseとNOTICEを確認し、Skill直下の`THIRD_PARTY_NOTICES.md`へ出典・version・licenseを記録する。esbuildはlegal commentを保持し、bundle再生成testでnoticeとpackage versionの一致を確認する。

### 4.5 UI構造

画面の情報順を次へ変更する。

1. snapshot、差分統計、承認進捗
2. Plan coverage summary、項目一覧、未確認verification一覧
3. 変更グループ一覧
4. 選択groupのレビュー詳細
5. `walkthrough`時だけファイル別解説view
6. finding、コメント、feedback copy

Plan項目はstatusで絞り込め、evidenceからgroupまたは該当diff位置へ移動できるようにする。group detailには関連Plan項目を表示する。runtime verificationはcoverage件数へ混ぜず、「未確認」と必要なcommand・目視内容を独立表示する。

ファイル別解説viewは左側に`(groupId, fileId)`単位のfile navigation、右側にfile summaryとsegment cardを表示する。同じpathが複数groupにある場合はgroup名を併記する。segment cardは説明を先に、対応コードを直後に置く。desktopではfile navigationをstickyにし、mobileではselectへ変える。

raw unified diffは削除せず、監査用の正本として残す。大きなhunkの400行lazy paginationも維持する。walkthroughのsegment codeは選択file・選択segmentだけを描画し、全segmentを初期DOMへ展開しない。

### 4.6 状態と互換性

- report schemaとUI stateをv3へ上げる。
- 既存のself-contained v2 HTMLはそのまま閲覧できるが、新generatorはv3だけを生成する。
- v2のlocalStorage stateはv3へ自動移行しない。古い承認を新しいPlan coverage・説明構造へ誤適用しないためである。
- group fingerprintはgroup ID、title、summary、changeType、risk、intent、implementationSummary、impact、verificationPoints、file metadata、tokenを除くraw hunk、finding fingerprintから計算する。
- group fingerprintからreport mode、Shiki token/style/highlighting metadata、Plan coverage、verificationItems、planItemIds、file explanation、segment、UI stateを除外する。同じ分析・snapshotから作ったreview/walkthroughとhighlighter再buildで承認状態を共有できるようにする。
- finding fingerprintはID、stage、severity、category、location、issue、rationale、suggestion、confidence、planAssessmentから計算し、Plan評価が変わったfindingのresolve状態は復元しない。
- file explanationとsegmentは安定IDを持つが、人間コメントと承認は従来どおりgroup単位にする。

## 5. 採用しない方針

- 変更グループを行数やfile数だけで自動分割しない。承認対象の実装意図が分断されるため。
- 詳細解説を全reportで必須にしない。小さい差分の生成時間と情報量を増やさないため。
- CSS正規表現だけの独自syntax highlighterを作らない。言語ごとの誤判定と保守負担をSkill側へ持ち込まないため。
- browserからCDN、npm、local serverへ接続しない。`file://`で完結するportable性を維持するため。
- Plan全文をBlind inputやStage 1へ渡さない。現在のBlind review保証を維持するため。
- 正常なコード説明をfindingへ変換しない。問題指摘、resolve、未解決件数の意味を維持するため。
- AST parser、Language Server、repository固有build toolを導入しない。多言語Skillとしての移植性と通常実行時の独立性を維持するため。

## 7. 実装手順

1. **評価fixtureを固定する**
   - siblingの`explained-code-review-workspace/skill-snapshot/`へ現行Skillを改善前baselineとして保存する。
   - 小差分、Planあり大差分、Planなし大差分の3ケースを`evals/evals.json`へ用意する。
   - 大差分caseは複数groupに同じfileが属する状態、1,000行超hunk、lockfile、finding、部分的なPlan不足、runtime完了条件を含める。

2. **v3分析契約を追加する**
   - Stage 1 analysisへmodeと、walkthrough時のgroup-scoped file explanation、detail level、segmentを追加する。
   - final analysisへPlan coverage、verificationItems、group/fileのPlan link、S2 findingを追加する。
   - evidenceは`kind: implementation | test | documentation`、`groupId`、任意の`file`、`lineSide`、`startLine`、`endLine`を持つ。file位置を持つ場合は該当groupのdiffと交差させる。
   - coverage item抽出からruntime実行条件を除外し、verificationItemsへ`not-verified`で移す。
   - Stage 1 group/hunk/説明の完全保持、S1 findingの許可変更、Plan item status/evidence/finding、group参照、file参照、line range、detail level別segment coverage、最大120行をsemantic validatorで強制する。
   - schemaからstandalone validatorを再生成する。

3. **collectorとSkill promptを更新する**
   - `--explain`をparseし、既定`review`、不正値error、blind/plan inputへのmode記録を実装する。
   - collectorがsummary-only kindとwalkthrough 20,000行上限を決定し、Blind inputへ分類結果を渡す。
   - Stage 1 promptはwalkthrough時だけfile/segment説明を要求し、論理単位、最大120行、説明長、反復禁止のrubricを渡す。
   - 4,000行または1 MiBごとのBlind batchとBlind consolidatorを実行し、いずれにもPlan情報を渡さない。
   - Stage 2 promptは静的Plan項目、runtime verification項目、status、evidence、group link、S2 findingを要求し、許可範囲外のStage 1変更を禁止する。
   - batchの結合時にもhunk・segment参照が壊れないよう、collector発行のhunk IDと`segment-<hunk-id>-<連番>`を使う。

4. **Shiki portable bundleを作る**
   - fine-grained language/themeとJavaScript engineだけを含むentrypointを作成する。
   - esbuildでNode 20向け単一ESMへbundleし、生成物へsource package versionとinput hashを記録する。
   - bundleは`createHighlighterCoreSync`を公開し、generatorの同期interfaceを維持する。
   - generatorでpathからlanguageを決め、old/new streamを規定どおりdual-theme tokenへ変換し、UTF-16 rangeと共通style tableへ圧縮する。
   - 1 MiBのtokenize入力、hunk token数、4倍＋固定overhead、hunk前後の10秒deadline、64 MiB report上限を順に適用し、理由付きでhunk単位fallbackする。元文字列不一致だけはデータ破損として停止する。
   - legal commentを保持し、third-party noticeとbundle input version/hashを検証する。

5. **Plan-first UIへ組み替える**
   - snapshot直後へPlan coverage summary、status filter、項目card、未確認verification一覧を表示する。
   - Plan evidenceとgroupの相互navigation、diff line focusを実装する。
   - group detailで関連Plan項目を先に示し、その後に実装意図、影響、確認ポイント、raw diffを置く。
   - token span、横scroll、line number、追加・削除・findingの重なりをlight/dark両方で調整する。

6. **walkthrough UIを追加する**
   - report modeが`walkthrough`のときだけview switchを表示する。
   - group-scoped file一覧にgroup名、path、責務、変更行数、segment数、Plan対応数、finding数を表示する。
   - segment選択時だけ説明と対応コードを描画し、前後segment移動とfile移動をキーボード操作できるようにする。
   - summary-only fileは理由とfile summaryを表示し、無意味なtokenized lockfile全文を初期表示しない。

7. **保存状態・feedback・文書をv3へ揃える**
   - view、selected file、selected segment、Plan filterをv3 localStorageへ保存する。
   - Markdown feedbackへPlanのpartial/missing、未解決finding、group commentを含める。
   - README、Skill metadata、利用例、開発build手順、portable制約、v2互換範囲を更新する。

8. **Skill評価を実行する**
   - 各evalについて改善版`with_skill`と改善前`old_skill`を同じターンでpair起動し、iterationごとのdirectoryへ出力する。
   - 各run完了時にtoken数、所要時間、秒換算を`timing.json`へ保存する。
   - assertionはPlan項目とruntime verificationの分離、evidenceの妥当性、segmentの論理的一貫性、1行segment乱造・説明重複・責務混在、findingとの分離、summary-only判定、portable生成を対象にする。
   - graderで各runを評価し、`grading.json`へ`text`、`passed`、`evidence`を保存する。
   - `scripts.aggregate_benchmark`でbenchmarkを集計し、analyzer passで非識別assertion、variance、時間・token tradeoffを確認する。
   - `eval-viewer/generate_review.py`で改善版と旧版、formal grade、benchmarkを表示し、利用者feedbackを保存する。
   - 指摘が残る場合はiteration 2を実行し、前iterationをviewerへ渡す。利用者が承認するか、具体的feedbackがなくなるまで反復する。

## 8. テスト・検証方法

### Unit / schema

- `--explain`の既定値、両mode、不正値を検証する。
- v3 reportで未知field、参照不能なPlan/group/file/hunk ID、不正line rangeを拒否する。
- `satisfied`なのにevidenceがない、`partial`/`missing`なのに不足理由がないreportを拒否する。
- runtime実行条件をstatic coverageとして`satisfied`にしたreportと、verificationItemsを`not-verified`以外にしたreportを拒否する。
- review modeでwalkthrough dataが混入した場合、walkthroughの`segmented` hunkにsegment coverageの欠落・重複・121行以上がある場合を拒否する。collector分類のない`summary-only`も拒否する。
- Stage 2がStage 1のgroup ID、hunk割当、group説明、file summary、segment説明、S1 findingの許可field以外を変更した場合を拒否する。
- S1 findingの`planAssessment`更新とS2 finding追加が許可され、S1 findingのgroup移動・本文変更・削除が拒否されることを個別に検証する。
- pathから対応言語を決定し、未知拡張子、Git meta、binaryをplain textへfallbackする。
- addition/contextはnew、deletionはold、metaはplain textを使うことを、削除後のcontext、複数行文字列、空行、`No newline` markerで検証する。
- Shiki token rangeから元のdiff lineを完全復元でき、`<script>`などの入力がHTMLとして実行されないことを検証する。
- light/dark token、font styleの許可field以外をreportへ入れないことを検証する。
- 同一snapshot・同一分析のreview/walkthrough、Shiki再build前後でgroup/finding fingerprintが一致し、groupの意味またはraw diff変更時は一致しないことを検証する。

### Generator / portability

- `pnpm build:highlighter`後の生成bundleがclean treeで再生成可能か確認する。

- `THIRD_PARTY_NOTICES.md`、bundle内legal comment、package version、build input hashの一致を検証する。

## 9. リスク

- **report肥大化**: token textを複製せずUTF-16 rangeと共通style tableへ圧縮し、hunk単位上限と64 MiB report上限を超えた強調だけをplain textへ戻す。
- **生成時間増加**: Shiki highlighterはgenerator起動中に1回だけ初期化し、同じ言語を再利用する。同期tokenizeの前後で10秒deadlineを確認し、超過した現在hunkの結果と残りhunkはplain textへ戻す。walkthroughのLLM説明は20,000行上限とBlind batchで制御する。
- **multi-line grammarの精度**: unified diffにはhunk開始前の状態がない。old/new streamを分け、contextはnew側を採用するが、強調はhunk内のbest effortであることをUI helpへ明記する。raw textは常に正本として保持する。
- **Plan項目の過分割・過少分割**: 見出しだけでなく、実装可能な箇条書きと静的に判定できる完了条件を項目にし、単なる背景説明とruntime実行条件はcoverage itemにしないルールをreview-rulesへ記載する。
- **test成功の誤認**: runtime完了条件をverificationItemsへ分け、今回のreportでは常に`not-verified`とする。test codeの存在だけで成功扱いしない。
- **説明と指摘の混同**: segmentにはseverityやresolveを持たせず、問題がある場合だけfinding IDを関連付ける。
- **既存承認の誤復元**: state versionを上げ、v2 stateを移行しない。v2 HTML自体の閲覧は壊さない。
- **bundle更新忘れ**: build input hashとpackage versionをbundleへ記録し、unit testでpackage manifestとの一致を確認する。
- **第三者assetの再配布**: legal commentを保持し、Shiki、theme、grammarのnoticeをSkillへ同梱する。
