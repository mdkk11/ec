# PRODUCT

## 1. この文書の目的

この文書は、ECテストサンドボックスで扱う機能、ビジネスルール、利用者、対象外を定義する。

このアプリケーションの主目的はECサービスそのものを完成させることではない。単体テスト、フロントエンド結合テスト、バックエンド結合テスト、E2E、VRTの責任範囲と運用方法を、現実的だが小規模な題材で検証できる状態を作ることを目的とする。

機能追加の判断では、ECとしての網羅性よりも次を優先する。

- 複数のテストレベルで扱える明確なビジネスルールがあること
- 正常、空、ローディング、エラー、競合を再現できること
- DBトランザクションや認可を含むバックエンドの境界が明確であること
- 自動テストを決定的かつ短時間で実行できること
- 実験対象でない機能を増やさないこと

## 2. 想定利用者

### 購入者

- 公開中の商品一覧と商品詳細を閲覧する
- ログイン後、商品をカートへ追加・更新・削除する
- クーポンを適用する
- 注文を確定する
- 自分の注文履歴を確認する

商品一覧と商品詳細は未認証でも閲覧できる。カート以降の操作はログインを必須とする。

### 管理者

- 商品を作成・編集・非公開化する
- 商品の在庫数を更新する
- 注文一覧を確認する
- 許可された範囲で注文ステータスを更新・取消する

管理者は購入者用アカウントとは異なる `admin` ロールを持つ。購入者が管理機能へアクセスした場合は権限不足として拒否する。

## 3. 対象機能と画面

| 区分 | 画面 | 主な状態・操作 |
| --- | --- | --- |
| 共通 | ログイン | 成功、認証失敗、送信中、サーバーエラー、セッション失効 |
| 購入者 | 商品一覧 | 商品あり、空、ローディング、取得エラー、在庫切れ表示 |
| 購入者 | 商品詳細 | 公開商品、在庫切れ、404、取得エラー、カート追加 |
| 購入者 | カート | 商品あり、空、数量変更、削除、在庫不足、更新エラー |
| 購入者 | 注文確認 | クーポン適用、合計表示、注文送信、条件変更による競合 |
| 購入者 | 注文完了 | 注文番号と確定内容の表示 |
| 購入者 | 注文履歴 | 履歴あり、空、ローディング、取得エラー |
| 管理者 | 商品管理 | 一覧、作成、編集、非公開化、競合 |
| 管理者 | 在庫管理 | 在庫数更新、入力エラー、競合 |

トップページは現在のVite試作の情報構成、コピー、ビジュアルをNext.jsへ引き継ぐ。ただし、Viteコードの互換性は維持せず、検索・お気に入り・仮カートなどローカルstateだけで完結していたデモ操作は移植しない。これらの機能は本書と開発計画で対象となるPhaseに、共通API境界を通して実装する。

## 4. 代表導線

### 購入導線

1. 未認証で商品一覧・詳細を閲覧する。
2. 購入操作時にログインする。
3. 商品をカートへ追加し、数量を調整する。
4. 必要に応じてクーポンを適用する。
5. 注文内容を確認し、注文を確定する。
6. 注文完了画面と注文履歴で確定内容を確認する。

注文確定に住所入力、配送方法選択、支払方法選択は含めない。注文合計は商品小計からクーポン割引を引いた金額とする。

### 管理導線

1. 管理者としてログインする。
2. 商品を作成・編集・非公開化する。
3. 商品の在庫数を更新する。
4. 注文を「受付」から順方向へ更新する、または許可された状態から取り消す。

## 5. ビジネスルール

### 5.1 認証と認可

- 認証方式はメールアドレスとパスワードによる簡易ログインとする。
- パスワードは平文で保存しない。
- ログイン成功時は暗号学的乱数からセッショントークンを発行し、生トークンはCookieだけに、SHA-256ハッシュはDBだけに保存する。
- セッションCookie名は `mockshop_session` とし、`Path=/`、`HttpOnly`、`SameSite=Lax`、有効期限7日を設定する。本番相当環境では `Secure` も付与する。
- 期限切れ、存在しない、またはハッシュが一致しないセッションは未認証として扱う。
- ロールは `customer` と `admin` の2種類だけとする。
- seedに購入者と管理者の検証用アカウントを用意する。
- カート・注文・注文履歴は `customer` だけに、管理機能は `admin` だけに許可する。`admin` は購入者機能を兼任しない。
- 会員登録、メール確認、パスワード再設定、アカウント編集、OAuthは実装しない。

### 5.2 商品

- 商品は単一SKUとし、色・サイズなどのバリエーションを持たない。
- 商品は名前、説明、価格、画像パス、公開状態、在庫数、バージョンを持つ。
- 価格は0以上の整数円とする。浮動小数点数では保持・計算しない。
- 在庫数は0以上の整数とし、負数への更新を許可しない。
- 購入者向けの商品一覧・詳細には公開中の商品だけを表示する。
- 在庫0の商品は閲覧可能だが、カートへ追加できない。
- 商品の削除は行わず、販売を止める場合は非公開にする。
- 注文済みの商品を後から編集しても、過去の注文表示は変化させない。

### 5.3 カート

- カートはログイン中の利用者ごとに1件持つ。
- カートは更新用の整数 `version` を持ち、明細追加・数量変更・削除、クーポン適用・解除、注文後のクリアで1増やす。
- 同じ商品を追加した場合は新しい行を作らず、既存行の数量を増やす。
- 数量は1以上の整数とする。0への更新ではなく削除操作を使う。
- カート投入・数量変更時点の在庫数を上限とする。
- カートに商品を入れても在庫は確保しない。
- 商品が非公開化された、価格が変わった、在庫が減った場合は、注文確認・確定時に最新値を表示または通知する。
- 非公開の商品はカートから自動削除せず、利用不可として保持する。非公開である間は注文できず、商品が再公開されるか購入者が明細を削除するとissueを解消する。
- カート表示時の価格は現在の商品価格とし、注文確定時に再取得して確定する。
- `GET /api/cart` は、カートのversion、商品ID・数量・商品名・単価・公開状態、クーポン条件、計算結果から決定的な `checkoutToken` を生成する。在庫数はtokenに含めず、注文時に別途検証する。

### 5.4 クーポン

- 1つのカート・注文に適用できるクーポンは1件だけとする。
- クーポンはコード、割引率、最低購入額、利用開始日時、利用終了日時、有効状態を持つ。
- コードは前後の空白を除去し、大文字に正規化して照合する。
- 割引率は1以上100以下の整数パーセントとする。
- 判定対象の小計は割引前の商品小計とする。
- 割引額は `floor(商品小計 × 割引率 ÷ 100)` とし、整数円へ切り捨てる。
- 合計金額は0円未満にならない。
- 利用開始日時は含み、利用終了日時は含まない。時刻判定はUTCで行う。
- コードの不存在、無効、開始前、期限切れ、最低購入額未達は別のエラーコードで識別できるようにする。
- カートで適用できても、注文確定時に最新の小計・時刻・有効状態で再検証する。
- クーポンはmigration、seed、テストfixtureで用意し、管理画面や管理APIから作成・変更しない。
- 利用回数上限、利用者別制限、商品別制限、定額割引、クーポン併用は扱わない。

### 5.5 注文と在庫

- 注文は、注文時点の商品名、単価、数量、商品ごとの小計、クーポンコード、割引率、割引額、注文合計をスナップショットとして保持する。
- 注文確定時に、カートが空でないこと、商品が公開中であること、最新価格、最新在庫、クーポン条件を再検証する。
- 注文リクエストは、直前の注文確認で受け取った `checkoutToken` を送る。サーバーはロック取得後にtokenを再計算し、一致を確認する。
- 在庫検証、在庫減算、注文・注文明細の保存、カートのクリアは1つのDBトランザクションで行う。
- 注文トランザクションは対象カートを最初にロックし、商品行を商品ID順にロックしてから公開状態、価格、在庫、クーポンを再検証する。
- 複数利用者が最後の在庫を同時に注文した場合、確保できた1注文だけを成功させる。
- 在庫不足などの競合ではHTTP 409相当を返し、注文を部分保存せず、在庫を負数にしない。
- 表示後の商品構成、価格、公開状態、クーポン条件の変更で `checkoutToken` が一致しない場合はHTTP 409相当とし、最新の注文内容を再確認するまで確定しない。
- 注文送信中は注文ボタンを無効化し、画面上の二重送信を防ぐ。同じカートへの同時リクエストはカートロックによって直列化し、最初の1件だけが注文を作成する。後続リクエストはクリア済みカートに対する `EMPTY_CART` として拒否する。
- 注文履歴にはログイン中の利用者自身の注文だけを `created_at` 降順、同時刻は `id` 降順で表示する。他利用者の注文IDを指定した場合は未存在と同じ404として扱う。

### 5.6 注文ステータス

注文状態は次の5種類とする。

| 表示名 | 内部値 | 説明 |
| --- | --- | --- |
| 受付 | `received` | 注文が確定した初期状態 |
| 処理中 | `processing` | 発送準備中 |
| 発送済み | `shipped` | 発送処理済み |
| 完了 | `completed` | 注文処理完了 |
| 取消 | `cancelled` | 注文取消済み |

許可する遷移は次のとおりとする。

- `received` → `processing`
- `processing` → `shipped`
- `shipped` → `completed`
- `received` → `cancelled`
- `processing` → `cancelled`

これ以外の遷移、同じ状態への更新、取消後の再変更は拒否する。取消時は注文明細の数量を在庫へ戻す。在庫復元と状態更新は1つのDBトランザクションで実行し、同じ注文を複数回取り消しても在庫を二重に戻さない。

### 5.7 管理更新と競合

- 商品、在庫、注文は更新用の整数 `version` を持つ。
- 管理画面は取得時の `version` を `expectedVersion` として更新APIへ送る。
- 更新条件にIDと `expectedVersion` を含め、成功時に `version` を1増やす。
- 管理画面からの在庫更新、注文時の在庫減算、取消時の在庫復元を含むすべての在庫変更で、在庫値と商品の `version` を同じUPDATE内で変更する。
- 更新件数が0件の場合は古い情報による競合としてHTTP 409相当を返す。
- 競合した画面は入力を勝手に再送せず、最新値を再取得して利用者へ差分確認を促す。

## 6. 状態設計の共通方針

データを取得・更新する主要画面では、少なくとも次を区別する。

- 正常: データと利用可能な操作を表示する
- 空: 初回利用者が次に行う操作を示す
- ローディング: 読み込み中または送信中であることを示す
- エラー: 再試行可能な通信障害、入力不正、権限不足、未存在を適切に分ける
- 競合: 他操作によって前提が変化したことと、最新状態を読み直す導線を示す

ローディング中に前のデータを隠すか維持するかは画面単位で決めるが、送信中の重複操作は防止する。遅れて返った古いリクエストで新しい表示を上書きしない。

## 7. 今回実装しないこと

- 商品バリエーション、カテゴリ、検索、絞り込み、並び替え、お気に入り
- 画像アップロード、画像変換、外部ストレージ連携
- 定額クーポン、複数クーポン、利用回数制限
- クーポンの管理画面・管理API
- 商品・注文の物理削除
- 在庫予約、入出庫履歴、監査ログ
- メール・Push通知
- マイクロサービス、多言語、多通貨、リアルタイム通信
- 本番デプロイ、運用監視、性能・負荷試験、災害復旧

## 8. 仮定

- UIとドキュメントは日本語で作成する。
- UIの操作、状態、エラーは日本語で表現する。Vite試作から引き継ぐブランド名、シーズン名、編集見出しに限り、固有コピーとして英語表記を維持する。
- 通貨はJPYのみで、金額は整数として扱う。
- ローカル開発とCIではpnpm 11を使用する。
- PostgreSQLはローカルとCIで再現可能な単一DBとして利用する。
- seedデータはテスト用途の架空データだけを含む。
- 現在のVite試作は情報構成、コピー、ビジュアルをNext.jsへ引き継ぐが、コード互換性と対象外のデモ操作は維持しない。
